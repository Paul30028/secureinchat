How the IP leak test works, and what it cannot see

By Paul · 2026-10-20

A leak test is only useful if you know what it actually measures. This is a plain description of every check in our IP leak test, how it reaches its verdict, and where it can be wrong. The full source is in the site repository.

The premise

If you use a VPN or proxy, websites should see the address of your VPN exit, not the address your internet provider gave you. A leak is any address, name or setting that still points at your real connection. The test runs entirely in your browser and compares several independent views of your connection.

1. Public IP

Our own server returns the address Cloudflare saw for your request, plus its network (ASN and organisation) and an approximate location. If you tick "I'm using a VPN or proxy", we check whether the network name looks like a hosting or VPN provider rather than a consumer internet provider.

How it can be wrong: that judgement is a guess based on the network's name. Residential VPN exits and some corporate VPNs look like ordinary providers and will be flagged as a warning, not a failure. Location comes from IP geolocation data and is often off by a city or more.

2. WebRTC

WebRTC lets a browser set up calls directly. To do that, the page asks a STUN server for your public address, and any web page can do this without a permission prompt. We query stun.cloudflare.com and read the candidate addresses the browser returns.

  • A srflx candidate is the public address as seen by the STUN server. If it differs from the public IP in check 1, WebRTC is going around your VPN or proxy. That is a leak.
  • A host candidate is a local network address. Current browsers normally replace it with a random .local name unless the page has camera or microphone permission, so you usually see the hidden form.

How it can be wrong: if UDP to the STUN server is blocked on your network, you will see no public candidate at all. That is not proof you are safe, only that the question could not be asked.

3. IPv6

Some VPNs tunnel IPv4 only. If your device also has IPv6, IPv6-capable sites can reach you through your provider's address, outside the tunnel. We fetch your address over IPv4 and over IPv6 separately, look up the network of the second address, and compare it with the network of your main address. Different networks mean IPv6 traffic is leaving outside your tunnel.

How it can be wrong: if the network lookup for the second address fails, we report a warning rather than guess.

4. Time zone

Your browser reports its system time zone no matter what your VPN does. We compare its offset with the time zone of your IP's location. A mismatch is a signal that anti-fraud systems read as "this person is hiding their location". It is a signal, not a leak in the strict sense, so it is shown as a warning.

5. Request headers

Proxies sometimes announce themselves with Via, Forwarded or X-Forwarded-For headers, and your Accept-Language may point at a different country than your IP. We list what arrived. Language mismatch is shown as information only, because it is a weak signal.

6. DNS

A DNS leak means your device asks your internet provider's resolver for domain names instead of your VPN's. A browser cannot observe which resolver answered, so the test needs a server that can. We run the authoritative DNS server for a domain used only for this. Your browser looks up six random names under it, and the server records the address of each resolver that asks. The page reads that list back and looks up whose network each resolver is on.

The verdict is careful because the test cannot know who your internet provider is. A resolver on the same network as your exit address passes. A resolver on another network is a warning, since it may be your VPN provider's. If you first run the test with the VPN box unticked, the page remembers those resolvers in the tab, and a resolver that answers both times is reported as a leak. A well-known public resolver such as Google or Cloudflare is shown as information, because the test cannot tell whether you or your VPN chose it.

How it can be wrong: if no lookup reaches our server, because of caching, filtering or a slow path, the result is a warning, never a pass. Browsers that send DNS over HTTPS to a provider show up as that provider's resolver, which is what is actually answering. The resolver address is kept in memory for ten minutes and not logged.

What a browser test can never see

  • Traffic from other apps. Only your browser is tested, and a VPN can protect the browser while a torrent client or another program connects directly.
  • What happens when the tunnel drops. Kill-switch behaviour has to be tested by disconnecting the VPN yourself.
  • Leaks that depend on a specific site, such as a service that embeds your real address in a request.

What leaves your browser

When you press the button, your browser contacts our server, api4.ipify.org and api6.ipify.org for your addresses, ipwho.is to look up a second address's network, and stun.cloudflare.com for WebRTC. Each of them necessarily sees your IP address. External requests carry no cookies and no referrer. We store nothing from the test. Details are in the privacy policy.

Reading the result

Run the test twice: once without the VPN to record your real network, and once with it on. A clean result means the checks above found nothing, not that nothing exists. If something fails, the tool page has a fix for each type of leak.
