What a blind relay can and cannot know

By Paul · 2026-10-20

"Zero-knowledge" is easy to say and hard to check. These are design notes on what a blind relay, the server type SecureInChat is built around, can and cannot know. They describe our current design. The clients are in development and have not been independently audited.

What a blind relay is

In a conventional chat service the server holds your messages and could read them. In a blind relay design the encryption keys stay on the devices, and the server only passes opaque encrypted payloads from one device to another. If the server is breached or compelled, it has no message content to hand over.

What it cannot know

  • The content of messages and files, because it never has the keys.
  • Names that exist only on devices. In our design a group's display name is local to each device and is never sent to the relay.

What it still knows

A relay that routes traffic cannot avoid learning some metadata. Be sceptical of any product that claims otherwise.

  • The network address a device connects from, as with any server.
  • When devices connect and when messages arrive.
  • The size of each payload, which can hint at its type.
  • The identifiers needed to route messages, such as which group a device joins.

Minimising this metadata, for example by not keeping connection history, is a design goal. Eliminating it is not realistic for a server that routes messages.

A job the server cannot do: enforcing admin rights

On a normal server, "only the admin may publish an announcement" is a database check. A blind relay cannot make that check without knowing who the admin is and what is being sent, which would undo the point of being blind. So the rule moves to the clients. In our design the group creator holds a signing key, announcements carry a signature, and every client rejects announcements it cannot verify. The cost is that admin rights belong to whoever holds the key, and losing it needs a recovery mechanism.

Removing a member

You cannot reach into a removed member's phone, so removal works by moving the group to new key material. The remaining members receive the new keys, the removed member does not, and later messages are unreadable to them. This has an honest limit: messages already delivered to the removed member's device stay readable there. It is also weaker than the continuous key ratcheting that Signal's protocol or MLS provide, and we do not claim equivalent security.

How to judge a "zero-knowledge" claim

  • Ask what the server can still see, and expect a specific answer about metadata.
  • Ask who can change group membership or publish as an admin, and where that rule is enforced.
  • Check whether the product separates design goals from independent audits and certifications.
  • Treat words like "100%" and "unhackable" as a reason to ask more questions.

You can see the relay's live handshake on the home page. That test shows that a secure connection to the relay works; it does not prove anything about what the server does with data, and we do not present it as proof of that.
