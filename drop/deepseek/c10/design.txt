C10 本地数据静态加密：方案比较与推荐
0. 现状与威胁模型

现状（附件源码）

主密钥 K1 是 extractable: false 的 AES-256-GCM CryptoKey，对象直接结构化克隆进 IndexedDB（secureinchat-master-key）。

EncryptedKeyValueStore 用 K1 对每个逻辑 key 的值做 AES-GCM，AAD 绑定 key 名。

敏感数据：groups:joined、messages:<groupId>、admin-key:<groupId> 走加密存储；device-identity:device-id、applock:v1、screensecurity:v1、biometricunlock:v1 是明文 IndexedDB；BrowserKeystore 的设备签名密钥也是 CryptoKey 直接存 IndexedDB。

应用锁 PIN 只做 PBKDF2 哈希比对，不参与加密；输错 10 次清空是应用层逻辑。

真实威胁：WebView 把 CryptoKey 的原始密钥材料序列化到应用数据目录。root、某些系统备份、取证工具拿到目录，就同时拿到 K1 和密文。extractable: false 只挡 JS，不挡文件。

防护目标（按 OTF 里程碑）

M1：拿到应用数据目录（无设备在线）读不出消息。

M2：捡到已解锁手机、不知道 PIN，也读不出消息。

不做：防设备被完全控制后、用户已通过所有认证的在线提取；防 rubber-hose。

A. 硬件密钥包裹主密钥（Android Keystore / StrongBox）

设计要点

新写 KeystorePlugin.java，在 Android Keystore 生成不可导出的 AES-GCM 密钥 HK；能用 StrongBox 时 setIsStrongBoxBacked(true)，失败回退 TEE。

JS 侧生成新的可导出主密钥 K2，导出原始字节后用 HK 加密，密文 + IV + 元数据存 IndexedDB。启动时请原生用 HK 解密，得到原始字节后 importKey 成不可导出的 K2 用于日常加解密。运行时主密钥仍不可导出，只是来源变成“解包”。

setUserAuthenticationRequired 的建议：设为 true，用 API 30+ 的 setUserAuthenticationParameters(timeoutSeconds, AUTH_BIOMETRIC_STRONG | AUTH_DEVICE_CREDENTIAL)（29 及以下用 setUserAuthenticationValidityDurationSeconds）。timeoutSeconds 建议 0（每次冷启动都要系统认证）或 300（5 分钟内复用）。

不设：设备解锁状态下 root 可直接调用 Keystore 解开，A 只防“离线拷文件”。

设了：root 也需要用户先过系统认证，才拿到 K2。代价是每次冷启动弹一次系统生物识别/设备 PIN——和应用锁 PIN 是两个东西，不冲突。

setInvalidatedByBiometricEnrollment 建议 false：设 true 更安全（别人新录指纹后密钥失效），但用户加指纹后数据不可读，UX 太差；我们的威胁模型不覆盖“设备已被完全控制”。

防得住

离线拷走应用数据目录：没有 TEE/StrongBox 里的 HK，K2 密文解不开。这是对“文件级提取”的真正防护。

StrongBox 设备上更强：独立安全芯片，TEE 被攻破也拿不到 HK。

应用卸载/清除数据会删 Keystore 密钥，数据自然不可读（和用户预期一致）。

防不住

设备在线 root 且 HK 未绑定用户认证：root 以应用 UID 调用 Keystore 解开 K2。绑定用户认证后，需要用户先过系统认证。

用户被胁迫解锁设备并过认证。

Web 端完全没有这个能力，只能保持现状。

PIN 很短时

和 PIN 无关。A 的强度来自硬件密钥，4 位 PIN 也不影响静态加密。但 A 不提供“忘 PIN 就解不开数据”的保证——清除 applock:v1 后数据仍可读。

迁移

旧 K1 不可导出，但可 decrypt。迁移不导出 K1，而是“读旧密文 → K1 解密 → K2 加密 → 写回”。

断电安全用双密钥 keyring + lazy migration（详见第 1 问）：K1 和 K2 的包裹信息并存；get 先试 K2 失败再试 K1，set 总用 K2；后台跑一遍全量迁移，完成后删 K1。每个条目写入是 IndexedDB 单 key 原子操作，断电后要么旧密钥要么新密钥加密，两种都能读。

首次启用需要一次系统认证（如果 HK 绑定了认证）。

忘记 PIN 的后果

和 A 无关。忘 PIN 只影响应用锁；如果能绕过应用锁（清 applock:v1），数据仍可读。A 不增加“忘 PIN 丢数据”的风险。

和 C9 备份的关系

C9 备份用备份密码派生的密钥加密 payload（群、消息、昵称的明文 JSON），不包含设备主密钥，也不依赖 HK。A 不影响备份生成和恢复；恢复时用新设备自己的 K2 加密写入。忘 PIN 后备份仍可用备份密码恢复。

实现量

新增 KeystorePlugin.java（生成/解包/删除 HK，StrongBox 探测与回退，用户认证参数）。

修改 MainActivity.java 注册插件；AndroidManifest.xml 通常无需新权限（USE_BIOMETRIC 已有）。

新增 apps/android-client/src/hardwareKeystore.ts（TS 封装，非原生平台返回不可用）。

修改 packages/crypto-core/src/persistentMasterKey.ts（或新增 masterKeyProvider.ts，按平台分派：原生用 HK 包裹，Web 保持现状）。

修改 apps/android-client/src/deviceIdentity.ts（getDeviceStore 用新 provider）。

新增 packages/secure-storage/src/masterKeyMigration.ts（双密钥 keyring + lazy/全量迁移）。

修改 packages/secure-storage/src/encryptedKeyValueStore.ts（双密钥读取，set 用当前密钥）。

修改 packages/crypto-core/src/index.ts 导出。

测试：hardwareKeystore.test.ts、masterKeyMigration.test.ts、deviceIdentity 回归。

UI：MessageListScreen 或新屏说明“本机数据受硬件密钥保护”；HK 解包失败时引导从 C9 备份恢复。

风险

Keystore 密钥失效（清数据、卸载重装、恢复出厂、罕见系统升级）→ 数据不可读，只能靠 C9 备份。必须检测并给出明确指引。

StrongBox 兼容性：部分设备有 bug 或密钥数量限制；必须捕获 StrongBoxUnavailableException 回退 TEE，并记录实际级别。

每次冷启动系统认证的 UX；timeoutSeconds 需要产品决策。

Web 端保护级别不一致，必须在文档/UI 里讲清楚。

B. PIN 派生密钥包裹主密钥

设计要点

PIN → PBKDF2-SHA256（迭代 600k 或更高）→ KEK_pin；用 KEK_pin 包裹 K2 的原始字节，密文存盘。启动时用户输 PIN 派生 KEK_pin 解包。

应用锁从“存哈希比对”改成“派生 KEK + 解包”；解包成功即 PIN 正确。

防得住

捡到手机但没 root、不知道 PIN：打不开应用，也解不开数据。

防不住（根本缺陷）

拿到应用数据目录 + 离线爆破。6 位数字 PIN 只有 100 万种；PBKDF2 210k 迭代在 GPU 上每秒可试几十万到几百万次，6 位 PIN 几分钟到几小时穷举完；600k 迭代只把时间乘以约 3。Argon2id 能提高内存成本，但 WebView 没有原生实现，纯 JS 实现慢且要加依赖（违反规则）。

“输错 10 次清空”是应用层逻辑，攻击者离线爆破不经过它。

4 位 PIN 更糟。

PIN 很短时

等同于没有静态加密。B 单独用会给用户虚假的安全感，是反模式。

迁移

同 A 的双密钥迁移；额外要求用户先设 PIN。已有应用锁用户可直接迁移；没设 PIN 的用户需要先设，或保持“未启用静态加密”。

忘记 PIN 的后果

K2 解不开 → 本机数据全部不可读。这是真正的“忘 PIN = 丢数据”，必须提前告知，并把 C9 备份作为唯一恢复途径。生物识别不能替代 PIN 解包（除非把生物识别成功当作允许调用 Keystore，那就变成 C）。

和 C9 备份的关系

备份用备份密码加密，不依赖 KEK_pin。忘 PIN 后备份仍可用备份密码恢复——这是 B 的唯一安全网，必须在 UI 里反复强调。

实现量

修改 apps/android-client/src/appLock.ts（PIN 派生 KEK_pin，不再只存哈希；disableLock 要处理“数据仍加密但无 PIN”的状态，或禁止关闭）。

新增 packages/secure-storage/src/pinWrappedMasterKey.ts。

修改 persistentMasterKey.ts、deviceIdentity.ts、encryptedKeyValueStore.ts、迁移模块（同 A）。

测试：appLock.test.ts 扩展、pinWrappedMasterKey.test.ts、迁移测试。

UI：设置 PIN 时说明“忘记 PIN 数据不可恢复，请先做备份”；关闭应用锁时的数据处置。

风险

离线暴力破解是根本缺陷，无法靠增加迭代次数解决。

忘 PIN 丢数据，用户支持成本高。

“未设 PIN”状态下的降级路径需要产品决策。

C. A + B 组合（硬件密钥 + PIN 两层）

设计要点（推荐的具体形态）

生成 K2（可导出，仅内存）。

PIN → PBKDF2 → KEK_pin；用 KEK_pin 加密 K2 得 C1。

用硬件密钥 HK（必须 setUserAuthenticationRequired(true)）加密 C1 得 C2，存盘。

启动：调用 KeystorePlugin 解 C2 → 得 C1（此时系统已要求用户认证）→ 用户输 PIN 派生 KEK_pin 解 C1 → 得 K2。

两层独立：硬件层挡离线爆破，PIN 层挡“设备已解锁、系统认证已过、但不知道应用 PIN”。

防得住

离线文件提取：需要 HK（TEE/StrongBox 内，不可导出），无法离线爆破 PIN。

设备在线 root：HK 绑定用户认证，root 也需要用户先过系统认证；过了系统认证还需要应用 PIN。

捡到手机：应用锁 PIN + 系统认证双重。

防不住

用户被胁迫交出 PIN 和设备解锁。

TEE 被攻破（StrongBox 降低风险）。

设备已解锁、用户已过系统认证、恶意应用以应用 UID 运行（root）→ 可拿到 K2。这是“设备被完全控制”，任何本地加密都防不住。

PIN 很短时

硬件层兜底，6 位 PIN 也不怕离线爆破。前提是 HK 正确绑定了用户认证；若 HK 不绑认证，root 可拿到 C1 后离线爆破 PIN，退化成 B。

迁移

同 A/B 的双密钥迁移，但迁移前需要用户设 PIN 并过一次系统认证。已有应用锁用户可直接用现有 PIN 派生 KEK_pin。

忘记 PIN 的后果

即使有硬件密钥，没有 PIN 也解不开 C1。忘 PIN = 丢数据，和 B 一样。C9 备份是唯一恢复途径，必须在 UI 里讲清楚。

如果希望“生物识别可作为 PIN 的后备”，需要把生物识别成功当作允许调用 Keystore 解 C1 的凭证——但这会削弱“PIN 是唯一后备”的定位，且生物识别绑定的是设备，换设备/重录指纹后不可用。建议不做。

和 C9 备份的关系

同 A/B：备份独立于 HK 和 PIN，忘 PIN 后仍可用备份密码恢复。这是 C 的安全网。

实现量

A 和 B 的并集，外加组合状态机（未启用 / 仅硬件 / 硬件+PIN / HK 不可用降级）。

KeystorePlugin 需要支持用户认证参数和 StrongBox 回退。

迁移需要同时处理 K1 → K2 和 K2 的两层包裹。

测试覆盖组合解包、任一层失败、降级路径。

风险

复杂度最高，一次交付风险大。

用户需要理解“系统认证”和“应用 PIN”是两件事，文案要清楚。

HK 失效 + 忘 PIN 同时发生 → 只能靠 C9 备份，必须有明确引导。

四个问题的回答
1. 迁移怎么做，中途断电怎么保证不丢数据？

不导出旧 K1：它 extractable: false，但可 decrypt。迁移是“读旧密文 → K1 解密 → K2 加密 → 写回”，全程不需要导出 K1。

断电安全用双密钥 keyring + lazy migration：

在 secureinchat-master-key DB 里存一个 keyring：{ v: 2, current: K2_wrapped, legacy: K1 }。K1 仍以 CryptoKey 形式暂时保留，K2 是新主密钥（被 HK/KEK_pin 包裹）。

EncryptedKeyValueStore.get 先试 K2 解，失败再试 K1 解；set 总用 K2。这样不需要改落盘格式，旧条目和新条目都能读。

后台跑一遍全量迁移：listKeys → 逐个 get（K1 解）→ set（K2 加密）。每个条目写入是 IndexedDB 单 key 原子操作，断电后要么旧密钥要么新密钥加密，两种都能读，不会丢数据。

全量迁移完成后删 K1，keyring 只留 K2。

迁移期间用户正常使用，新写入的条目天然用 K2。

替代方案：一次性在 IndexedDB 事务里迁移。数据量小的话可行，但跨数据库（secureinchat-master-key 和 secureinchat-storage）不支持事务，仍需双密钥过渡。所以推荐 lazy + 全量后台迁移。

K2 的可导出性：生成时 extractable: true，导出原始字节后用 HK/KEK_pin 包裹，然后丢弃原始字节，importKey 成 extractable: false 用于日常。运行时主密钥仍不可导出。

2. 管理员私钥和设备签名密钥要不要纳入？

管理员私钥：已经以恢复码文本形式存在 EncryptedKeyValueStore（admin-key:<groupId>），随主密钥升级自动获得新保护级别，不需要额外工作。但恢复码本身如果被用户抄在纸上，那是另一个泄露面，不在本轮范围。

设备签名密钥：BrowserKeystore 用不可导出的 CryptoKey 直接存 IndexedDB（device-identity:signing-key），和主密钥有同样的问题——原始材料在文件里。应该纳入，但建议分两步：

短期：用主密钥包裹它的原始字节（需要它 extractable: true，改 BrowserKeystore 的生成参数），存包裹密文，启动时解包。改动集中在 crypto-core 的 BrowserKeystore 和 deviceIdentity.ts。

长期：把设备签名密钥移到 Android Keystore（KeystorePlugin 生成 EC 签名密钥，签名操作在原生侧做）。改动面较大（RelayClient 的签名调用要变成异步原生调用），建议作为独立里程碑，不在 M1 塞进来。

3. 老 Android WebView 存不了 CryptoKey 的坑怎么避免？

新方案天然避开：主密钥不再以 CryptoKey 形式存盘，而是以“包裹后的密文字节”（Uint8Array）存盘。Uint8Array 的结构化克隆支持远比 CryptoKey 广，老 WebView 不会有问题。硬件密钥在 Android Keystore 里，不经过 WebView 的 IndexedDB 序列化。解包后得到的 K2 是内存态 CryptoKey，不落盘。

遗留问题：BrowserKeystore 的设备签名密钥仍存 CryptoKey。如果本轮纳入（见第 2 问），一并改成包裹密文；如果不纳入，这个坑仍在，需要在文档里标注为已知限制。

4. 推荐哪一种，为什么？

推荐：A 作为 M1 交付，C 作为 M2 目标架构。B 单独使用不推荐。

理由

B 单独用是反模式：6 位 PIN 离线爆破几分钟到几小时，防护几乎为零，还给用户虚假安全感。增加 PBKDF2 迭代无法解决根本问题；Argon2 在 WebView 里没有原生实现且要加依赖。

A 直接命中 M1：“拿到应用数据目录读不出消息”。实现量可控（一个新原生插件 + 主密钥 provider + 双密钥迁移），迁移路径清晰，断电安全。风险主要在 Keystore 兼容性和密钥失效的 UX，都可控。

A 单独不满足 M2：“捡到已解锁手机、不知道 PIN”时，如果 HK 没绑用户认证，root 可解开；即使绑了认证，用户过了系统认证就能解开，不需要应用 PIN。所以 M2 需要 C 的 PIN 层。

C 一次交付风险大：要同时改应用锁语义（PIN 从哈希比对变成派生 KEK）、Keystore 认证绑定、双密钥迁移、降级路径。分阶段先拿 A 的收益，再补 B 的“防捡到手机”，更稳。

和 C9 的关系：三个方案都不影响备份格式和恢复；忘 PIN 后备份是唯一恢复途径，这一点在 C 里尤其要在 UI 里讲清楚。

如果 OTF 里程碑的验收是“root 后拷走数据目录读不出消息”，A 就够，可以先把 M1 交付。
如果验收是“捡到手机、不知道 PIN，也读不出数据”，必须上 C。建议在方案文档里明确两者的边界，不要夸大 A。

A 的具体配置建议

HK 设 setUserAuthenticationRequired(true)，timeoutSeconds 建议 0 或 300，authTypes 用 AUTH_BIOMETRIC_STRONG | AUTH_DEVICE_CREDENTIAL。

尝试 StrongBox，失败回退 TEE，并记录实际级别（用于 UI 说明和诊断）。

setInvalidatedByBiometricEnrollment(false)，避免用户加指纹后数据不可读；如果团队更看重安全性，可设 true 并在 UI 里明确告知。

解包失败时（HK 失效）给出明确提示：“本机数据无法解密，请从备份恢复”，并引导到 C9 的 BackupScreen。

需要在方案里明确写清楚的“不夸大”边界

A 防“离线拷文件”，不防“设备已解锁且用户已过系统认证的在线提取”；C 增加 PIN 层，但仍不防设备被完全控制。

Web 端没有硬件 Keystore，保持现状（不可导出 CryptoKey 存 IDB），保护级别低于 Android 原生；必须在文档和 UI 里说明。

忘 PIN（B/C）数据不可读，C9 备份是唯一恢复途径；备份密码强度（至少 10 字符）远高于 6 位 PIN，这是真正的恢复保障。

不做“安全码”（Paul 已否决），所以没有 PIN 之外的本机后备。

管理员私钥随主密钥自动覆盖；设备签名密钥的硬件化是后续里程碑，不在本轮承诺。
