## 网站是什么
- SecureInChat:一个保护个人隐私的项目。使命：保护个人隐私这项基本人权。
- 三部分:
  1. 免费的隐私工具，大多数在浏览器里本地运行(照片元数据清除、文本脱敏、密码泄露检查、链接检查、浏览器指纹测试、隐私体检等);
  2. 写给普通人的隐私指南;
  3. 一个正在开发的端到端加密群聊 App(Mizpah):小团体的私密公告栏 + 群聊，中继服务器只转发它解不开的密文。
- 读者是普通人，不只是技术爱好者：要一眼看懂这是什么、能帮我做什么、下一步点哪里。

## 事实：聊天 App 威胁模型(Messaging 页的内容必须与此一致)
    Messenger threat model
    Last updated: 2026-11-05
    What the SecureInChat messenger is designed to protect, from whom, and what it cannot hide. The apps are in development and have not been independently audited, so this describes the design, not verified behaviour.
    What it is designed to protect
    
      The content of messages and files. Keys stay on the devices, and the relay only forwards encrypted payloads it cannot decrypt.
      Group names. In the design a group's display name exists only on each device and is never sent to the relay.
      Announcements from the group admin. They carry a signature from the creator's key, and every client rejects announcements it cannot verify.
    
    How a group key reaches members
    There is no public-key exchange between members. When a group is created, the app generates a random group key and puts it inside the invite code (the link or QR code). Whoever has a valid invite code can join and read the group's messages. Treat an invite like a house key: share it only in person or through a channel you trust.
    Who it is designed to resist
    
      Someone who breaches the relay, or compels its operator to hand over data. The relay has no message content and is designed without persistent storage of message content.
      Someone watching the network between a device and the relay. Connections use TLS, and the payload inside is encrypted again end to end.
    
    What the relay can still see
    A relay that routes messages cannot avoid some metadata. In the current design it sees:
    
      The network address each device connects from. The relay uses it only to limit repeated connection attempts and keeps a salted hash rather than the address itself; the hosting provider and any network or tunnel in front of the relay (currently Cloudflare) can still see it.
      When devices connect and when messages arrive.
      The size of each payload, which can hint at its type.
      The identifiers needed to route messages, such as which group a device joins.
    
    Not keeping connection history is a design goal. Removing this metadata entirely is not realistic for a server that routes messages.
    What it does not protect against
    
      A compromised phone. Malware, or someone holding your unlocked device, can read what you can read.
      People in the group. Anyone who receives a message can copy it, screenshot it or forward it.
      A leaked invite code. Anyone who gets it can read the group until the admin changes the key and sends a new invite only to the people who should stay.
      A key that leaks later. Each group key is used for every message until it is changed, so there is no forward secrecy within that period: if the key leaks, recorded messages from that period can be decrypted.
      Removed members keeping old messages. Removal moves the group to new keys, so later messages are unreadable to them, but messages already delivered stay on their device.
      Losing the admin key. Admin rights belong to whoever holds the creator's signing key, so losing it needs a recovery step.
    
    How it compares
    Group key changes on removal are weaker than the continuous key ratcheting that the Signal protocol or MLS provide. We do not claim equivalent security.
    Building blocks
    
      AES-256-GCM for authenticated encryption of each message.
      HKDF-SHA-256 to derive each key period's encryption key from the group key in the invite.
      ECDSA P-256 signatures for device sign-in to the relay and for admin announcements.
    
    These name the primitives in the design. They are not a certification. More detail: what a blind relay can and cannot know. You can check the live relay connection from your browser.
