# secureinchat 项目手册

给接手的人（包括未来的自己）看的一份总览。**只写事实和真正做过的决定**，
不写计划、不写宣传。

最后更新：2026-08-15
分支：`feature/protocol-crypto-core-scaffold-push`

---

## 1. 这是什么

邀请制的端到端加密群聊，给小团体用（教会/团契场景：每日经文、灵修短语、
赞美圣诗、通知）。**打开应用第一眼是「今日」四个栏目，不是会话列表**——
这是和所有通用 IM 最大的区别，因为公告每天更新、是很多人打开它的第一个理由。

没有账号、没有手机号、没有通讯录、没有搜索。**只能通过邀请码或扫码加入**。

## 2. 仓库结构

```

packages/

  crypto-core/           AEAD、HKDF、epoch、设备密钥、管理员签名
  secure-storage/        加密键值存储（AAD 绑定）
  chat-core/             中继客户端、消息信封、文件分片、离线队列、

  ui/                    9+ 个展示组件 + 设计令牌 + 线条图标

```

## 3. 架构上的硬约束（改动前必读）

### 3.1 中继是盲的

服务端**只见密文**。它不知道消息内容、文件名、群名、谁是管理员、谁被 @ 了。
它知道的只有：谁（deviceId）在哪个群（groupId）在线、谁给谁发了多大的密文。

由此推导出的一串结论，都不是"没做完"：

| 想要的东西 | 为什么做不了 |
|---|---|
| 服务端校验谁能发公告 | 公告和普通消息一样是密文，服务端分不出来 |
| 服务端"踢人" | 没有成员状态；就算踢了，对方手里的群密钥照样能解密 |
| 服务端离线暂存消息 | 中继按设计不保存任何消息 |
| @提醒推送 | 服务端不知道谁被 @ 了 |
| 换设备看历史消息 | 消息只在本机 |

### 3.2 管理员是密码学的，不是服务端的

建群者生成一对 ECDSA P-256 密钥：**公钥进邀请串**（人人可验证），**私钥留本机**。
公告必须带签名，签名覆盖 `groupId + 栏目 + 标题 + 正文 + 时间戳 + 音频ID`——
所以一条合法签名既不能换到别的栏目，也不能搬到别的群，也不能换掉音频。

- 本地"解锁管理员界面"**不构成权限**：没有私钥，别人的客户端会拒绝你的公告
- 换手机用**恢复码**（`SICADMIN1.` 开头）找回，它等同于管理员身份
- 恢复码的实现：密钥先以可导出方式生成 → 导出一次做成码 → **重新以不可导出
  方式导入**用于日常签名 → 丢弃可导出句柄

### 3.3 移出成员 = 换钥匙

新密钥材料、epoch 加一、新邀请码只发给留下的人。

两个必须说出口的限制（界面上也写了）：
1. **追不回**对方已经收到的消息——明文早在他手机上
2. 谁拿到新码谁就能进来，发错人等于白换

epoch **不高于**当前的邀请码会被忽略,否则重放旧邀请码就能把群降级、
让被移除的人重新读到。

## 4. 踩过的坑（最有价值的部分）

### 4.1 老 Android WebView 存不了 CryptoKey ⚠️ 踩了两次

把 `CryptoKey` 对象放进 IndexedDB 依赖结构化克隆支持 CryptoKey，
**Android System WebView 不一定支持**，而且失败是 `put()` **同步抛出**的，
事务的 `onerror` 根本接不到。

测试环境的 fake-indexeddb 支持它，所以**沙箱里怎么测都测不出来**。

- 表现：建完群进不去、扫码没反应、公告入口不出现——症状和真实原因毫无关系
- 现在：管理员密钥改存**文本**（和恢复码同一串），用时再导入
- 现在：启动时 `capabilityCheck.ts` 先测一次，不行就在第一屏说清楚
- 还剩两处仍在存 CryptoKey（`browserKeystore`、`persistentMasterKey`），
  已加同步捕获并给出可读错误

### 4.2 顺序错误会把人锁在门外

原来是「先存管理员密钥 → 再连接」。存失败就整个断在建群这一步。

**原则:便宜的失败排后面**。存不上最多发不了公告(恢复码可补救),
连不上是被锁在自己刚建的群外面、应用内无法补救。

### 4.3 APK 打包没带服务器地址

CI 从没设 `VITE_RELAY_URL`，所以每个包都指向 `ws://localhost:8765`——
手机上不存在的服务。扫码、加群、建群全卡在同一处，症状看起来像四个不相干的问题。

现在 workflow 里写死 `wss://ws-next.secureinchat.com`，应用内设置仍可覆盖。

### 4.4 公告只有自己看得见

接收方要用邀请串里的管理员公钥验签，但**已加入的群是从本地恢复的**，
而 `JoinedGroup` 没存这个字段。重连一次之后公钥就是 undefined，
所有公告验签失败、**被静默丢弃**。

定位方法值得记住：先写了个**双客户端跑真实中继**的测试，证明传输和签名都没问题，
才把范围缩到接收方的公钥上。没有这一步就只能猜。

### 4.5 CI 是 Node 20，沙箱是 Node 22

这个差异造成过两次真实失败：
- `crypto.randomUUID`、`navigator` 这些全局在 Node 20/老 WebView 上没有，
  而且**直接访问抛 ReferenceError，try/catch 接不住**（catch 只保护 await）
- 跑真实加密的测试在慢机器上超过 vitest 默认 5 秒 → 超时改成 30 秒，
  **而不是**降低加密强度让它跑得快

**CI 挂但本地过时，先查 Node 版本差异。**

### 4.6 flex 溢出

`flex: 1` 但没有 `minWidth: 0` → 输入框不收缩 → 把发送按钮顶出屏幕。
窄屏必现。按钮要 `flexShrink: 0` 保住 48dp。

### 4.7 React 的 dangerouslySetInnerHTML

同一个元素既传 `dangerouslySetInnerHTML` 又传 children，React 会丢掉一个——
二维码空白就是这样。而且 qrcode 生成的 SVG **没有宽高属性**，容器必须撑开它。

### 4.8 注册表持久化打断了测试

设备注册表改存 SQLite 之后，跨语言测试第一次能过、之后永远
`device already registered`。测试要用 `SECUREINCHAT_DEVICE_DB=:memory:`。

### 4.9 限流打到自己人

连接限流原本 30 秒 10 次。**一家人或一个办公室共用出口 IP，几个人同时开应用
就会互相挤掉**。已放宽到 60 次。限流打到正常用户身上比不限还糟。

### 4.10 sendEnvelope 不会失败

断线时它**排队**而不是抛错，重连后自动补发。所以：
- 没有"发送失败"这个状态，"点击重发"会和离线队列重复发送
- 真正该做的是标出"等待发送"，别让人以为对方已经看到了

## 5. 部署

```
ws.secureinchat.com       → 127.0.0.1:8765   旧中继（生产，不要动）
ws-next.secureinchat.com  → 127.0.0.1:8766   本项目
```

同一台 VPS（212.135.212.22）并行运行，各自 systemd 服务。
新中继的服务名 `secureinchat-next`。Cloudflare Tunnel 是 token 模式，
路由规则在网页控制台的 Published application routes。

**两套协议不互通**：旧中继握手用 `challenge` 字段，我们用 `nonce`。
`scripts/probe-relay-protocol.py` 可以判断任意地址说的是哪套。

更新：`cd /opt/secureinchat-next && git pull && systemctl restart secureinchat-next`

⚠️ `server/relay/devices.db` **需要备份**。删掉它等于让所有设备重新走首次注册，
TOFU 保护会重新开一次窗口。

## 7. 已知缺口（不要说成做完了）

- **MLS 没有实现**。只有共享群密钥 + epoch 轮换，前向保密只覆盖"移除成员后的新消息"。
  **不能声称达到 Signal 级别**
- 中继 `main.py` **没启用成员资格校验**：任何设备 claim 哪个 groupId 就能进哪个群。
  修它需要客户端认证时带邀请码，会导致新旧 APK 不兼容、所有人必须同时更新
- **TURN 没部署**，跨运营商通话连不上。同一 WiFi 应该能通
- 管理员权限绑在建群那台设备，恢复码是唯一退路，且它等同于管理员身份
- 应用锁保护"手机被别人拿起"，**不加密消息**（消息用设备主密钥，和 PIN 无关）
- 单个媒体超过 512KB 只在本地留元信息；每群消息上限 300 条
- 39 个规划界面里约 31 个没做
- 第九节清单还缺：已读回执、最后在线、生物识别、截屏保护
- **Paul 明确否掉了安全码验证（不要安全码），不要再提**
- 语音消息显示 0:00：WebView 自带控件读不到 webm 的时长元数据，能播但时长不准

## 8. 工作方式

- Paul 只审核发布类决定（合并 main、正式 Release、替换生产服务器、
  上架、删旧仓库）。其余自主推进
- **当前优先级：先把功能做完给团队用，安全往后放**
- **不要假功能**。占位数据和点了没反应的按钮浪费他的真机测试时间。
  已经因此清理过一批（写死的群名/成员数/邀请人、什么都不做的 + 按钮、
  写死的"刚刚"时间戳）
- 功能要成批交付，方便他一次测完
- 交接要简短：仓库/分支/提交/CI 链接、真正做完了什么、还差什么、安全缺口

## 9. 判断准则（从这个项目里长出来的）

1. **能力不足要在第一屏说，不要在第三屏炸**。用真实原因失败，好过用
   指向不明的症状失败
2. **测试要盯住真实行为**。"组件渲染了"测不出二维码空白；
   断言 `minWidth: 0` 才能测出布局溢出
3. **不稳定的测试要删或修根因，不要打补丁**。CI 随机变红,时间久了大家
   就开始忽略红灯,那比没有测试更糟
4. **先写测试定位，不要猜**。公告那个 bug 就是用双客户端集成测试
   把范围从"传输"缩到"接收方公钥"的
5. **限制和代价写在界面上**，不要让用户自己撞出来（换密钥追不回旧消息、
   改群名只改本机、退群删本地记录、恢复码等同管理员身份）
