# 多管理员与管理员签名的设备名单(C-ADM / C-ROSTER,草案 v1,2026-11-04)

状态:**设计草案 + 核心逻辑原型,待 Paul 审查。** 核心逻辑在 `packages/crypto-core/src/adminSet.ts`、
`deviceRoster.ts`,有单元测试,**没有接进 App、没有改邀请串和消息信封、没有改中继**。界面上什么都没多。
分支 `feature/C-ADM`,基于 `feature/C-REL`(本设计第 6 节依赖 C-REL 的开群凭证 `ras`;合并本分支会一并带入 C-REL 的设计文档)。

## 1. 现状(按 feature/chat c8e0ae1 的代码核对)

- 一个群只有**一把**管理员密钥:建群时生成(`adminSignature.ts` 的 `generateAdminKeyPair`),
  公钥作为 `apk` 写进 SIC2 邀请串(`packages/protocol/src/sic2/codec.ts`),私钥只在建群那台设备,
  靠恢复码 `SICADMIN1.` 换手机。
- 收公告时 `App.tsx` 用群记录里的 `adminPublicKeyRawB64Url` 调 `verifyAnnouncement`;签名不覆盖「谁签的」,
  因为只有一把钥匙。
- 想让第二个人也能发公告,唯一办法是把恢复码给他——等于把主管理员身份整个交出去,而且收不回来。
- 群里有哪些设备:`knownDevices.ts` 只记录**本机观察到的** deviceId(在线推送、收到的消息),
  没有任何人「认可」过这份名单。deviceId 是随机的 `device-<uuid>`,每台设备有一把 P-256 设备密钥,
  在中继上 TOFU 注册(`RELAY_CONTRACT_V0.md`),但群里其他成员**拿不到**这把公钥。
- 收到的每一帧带中继盖上的 `fromDeviceId`。消息本身不带设备签名,所以「这条是 device-X 发的」
  靠的是中继诚实(中继在握手时验过设备密钥)。

## 2. 目标与非目标

目标
1. 主管理员可以授权副管理员发公告、批准设备,并且**随时撤销**,撤销后对方签的东西所有客户端都不再接受。
2. 群里每台设备是否被管理员认可,App **自动**判断并标出来;不让用户互相核对数字(不做安全码,Paul 已否决)。
3. 一人一码:管理员可以给具体某个人发邀请,对方入群时 App 自动认出「这就是发给张三的那张」,不用管理员手动确认。
4. 中继不多知道任何东西:名单、申请、授权都走加密消息。
5. 老客户端不崩、不被锁在门外。

非目标
- 不防主管理员本人作恶或恢复码泄露(和今天一样;泄露了只能重建群)。
- 不做门限签名(多个管理员共同签才生效),见第 9 节。
- 不让中继按设备名单拦人:那需要中继知道群成员构成,违背手册 3.1。中继这一层仍按 C-REL 做「持有当前 epoch 材料」的检查。
- 名单不能代替换钥匙:把设备从名单里删掉,它手里的群密钥照样能解密,真正移出仍是换钥匙(手册 3.3)。

## 3. 多管理员(C-ADM)

### 3.1 模型:主管理员 + 副管理员名单

- **主管理员** = 建群时那把密钥(邀请串的 `apk`)。永远有效,不能被撤销。
- **管理员名单**(`SignedAdminSet`):主管理员签的一份文件 `{groupId, version, deputies[{公钥, 称呼}], issuedAtMs}`。
  `version` 从 1 开始,每改一次加一。
- **只有主管理员能改名单。** 副管理员能发公告、批准设备(第 4 节),不能加减管理员。

为什么不让副管理员也能改名单:两个副管理员可以互相撤销,各自签出同号的名单,客户端就得有一套
「谁说了算」的规则,很容易被利用(先撤销对方再干坏事)。只让主管理员改,名单就是一条直线,没有分叉。
代价:主管理员的恢复码丢了,名单就冻结了(副管理员仍能发公告和批准设备,但不能加新管理员)。

### 3.2 签名与校验(已实现,`adminSet.ts`)

被签名的字节:`"secureinchat:admin-set:v1\n" + JSON([groupId, version, 按公钥排序的 [公钥, 称呼], issuedAtMs])`,
ECDSA P-256 / SHA-256,P1363 格式(和公告签名、中继设备认证同一种)。

客户端收到名单:
| 情况 | 处理 |
|---|---|
| 主管理员签名不对、群号不对、结构不合格(主管理员写进名单、重复公钥、超过 16 人) | 丢弃(`invalid`) |
| 版本 ≤ 本机已有的 | 丢弃(`not-newer`)。**防回滚**:重放旧名单不能让被撤销的人复活 |
| 同版本但内容不同 | 保留本机的(`conflict`),在管理员页面提示「主管理员在两台设备上同时改了名单」 |
| 版本更大 | 换成它 |

名单本身是自证的(只认主管理员签名),所以**谁转发都可以**:新成员入群后任何在线成员都能把最新名单发给他。

### 3.3 公告怎么带签名人

公告信封(`AnnouncementEnvelope`)加一个可选字段 `adminKeyId` = base64url(SHA-256(签名人公钥))。
接收方用 `resolveAdminKey` 在**当前**名单里找这把钥匙:找到就用它验签;没带 `adminKeyId` 就当主管理员(老公告照常);
找不到(被撤销、伪造)就不当公告。公告签名输入(`announcementSigningInput`)不用改——换一把钥匙签的签名,
用另一把钥匙验不过,不存在「挪签名」的问题。

### 3.4 撤销的时序

撤销看的是**收到时**的名单,不是公告里写的时间:被撤销的人把 `sentAtMs` 往前写也没用。
已经显示过的旧公告不追溯删除(和手册 3.3「追不回已收到的消息」一致),界面可以给它标「签发人已被撤销」。

撤销副管理员时 App 应同时:①签新名单;②用主管理员重签一份设备名单(第 4.4 节,因为他签过的设备名单随之失效);
③问主管理员要不要顺便换钥匙(他如果也要离开这个群)。

### 3.5 副管理员怎么得到自己的密钥

副管理员在**自己的手机**上生成一把新的管理员密钥(复用 `generateAdminKeyPair`,同样有恢复码),
把公钥用加密消息发给主管理员(「申请成为管理员」),主管理员点同意 = 签新名单。私钥从不离开副管理员的手机。

## 4. 设备名单(C-ROSTER)

### 4.1 名单

`SignedRoster = {body: {groupId, version, adminSetVersion, entries[{deviceId, 设备公钥, 昵称, 批准时间}], issuedAtMs}, 签名人公钥, 签名}`。
签名人必须是**当前**有效的管理员(主或副)。`adminSetVersion` 记录签发时依据的管理员名单版本,
本机名单版本落后时先不采纳,等管理员名单同步。

同版本两份不同名单(两个管理员同时批准了不同的人):取正文哈希较小的那份。所有客户端算法一样,
**无论先收到哪份,最后停在同一份**(测试里验证了这一点)。落选那位管理员的 App 看到自己批准的设备不在名单里,
就在更高版本上重签一次(`nextRosterBody` 会保留现有条目再加上它)。

### 4.2 入群申请

新设备入群(用任何邀请)后,发一条加密的「入群申请」:`{groupId, deviceId, 设备公钥, 昵称, inviteTag?, 时间}`,
用**设备私钥**签(通过 `KeystorePort.sign`,私钥不出 Keystore)。这把设备密钥就是它在中继注册的那把,
所以申请同时证明了「这个 deviceId 背后是这把钥匙」。

### 4.3 自动判断(管理员的 App,`decideJoinRequest`)

| 情况 | 结果 |
|---|---|
| 申请签名不对 | 拒绝(不显示) |
| deviceId 已在名单且公钥相同 | 无事 |
| deviceId 已在名单但公钥不同 | 交给管理员(「这台设备的钥匙变了」) |
| 带了邀请标记,对得上一张**没用过**的一人一码邀请 | **自动批准**,昵称默认取那张邀请的备注 |
| 对得上一张**用过**的邀请(包括同一台设备被移出后又来) | 交给管理员(「这张邀请已经被用过」) |
| 没有标记 / 对不上 | 交给管理员 |

不自动拒绝:用普通邀请(群二维码)进来的人照样可以被手动批准。

### 4.4 一人一码

- 管理员发邀请时可以选「发给某个人」,写个备注(如「张三」)。App 生成 32 字节随机「邀请秘密」,
  放进这一张邀请串的新可选字段 `ivs`,并在管理员本机加密存储里记下 `{秘密, 备注, 用过没有}`。不广播。
- 对方入群后,申请里带 `inviteTag = HMAC-SHA256(邀请秘密, groupId + deviceId + 设备公钥)`。
  标记绑定设备:群里别人看到这个标记,也不能拿去替自己的设备申请;没拿到那张邀请的人算不出来。
- 邀请串里仍然有群密钥,所以**一人一码不能防止邀请被转发后别人进群**——它做的是让「转发后的第二个人」
  自动被识别出来交给管理员,而不是悄悄混进名单。界面和文档都要这样写,不能写成「防转发」。

### 4.5 成员这边看到什么(自动校验)

每个成员的 App 用 `checkObservedDevices` 拿名单对照自己看到的设备:
- 名单内:昵称旁显示「已由管理员确认」(不是数字,不需要比对)。
- 不在名单:群顶部一条提示「有 1 台设备还没被管理员确认」,点开列出来。消息照常显示、带标记——
  过渡期大量老客户端不会发申请,直接屏蔽会把正常成员挡掉。
- 同一 deviceId 公钥对不上:更醒目的提示。
- 管理员还没发布过名单:不提示任何东西(只在管理员页面说明这个功能)。

### 4.6 已知限制(必须写进文档和界面说明)

1. **消息不带设备签名时,「这条消息来自 device-X」仍靠中继诚实。** 名单能自动发现「不认识的设备在群里」
   (外人拿到邀请、被移出的人还没换钥匙),但一个作恶的中继可以给帧盖上名单内的 deviceId。
   要做到端到端,需要每条消息带设备签名(第二阶段,见第 9 节)。
2. 名单只在本机观察到的设备上起作用:没上线、没发过消息的设备看不到,就不会被标出来。
3. 从名单删掉 ≠ 移出群,要换钥匙。

## 5. 隐私:中继和成员各多知道什么

- **中继**:什么都不多知道。名单、申请、管理员名单都是普通加密 `forward` 帧(盲中继原则,`messageEnvelope.ts` 开头的设计决定)。
  多出来的只是这些帧的大小和时间:一份 50 台设备的名单按字段长度估算约 10 KB 密文(未实测)。
- **成员**:能看到名单里所有设备的昵称和 deviceId——今天的在线名单本来就暴露 deviceId,昵称随消息发送。
  新增的是设备公钥(不是秘密)和「谁是副管理员」(公告上本来就要显示)。

## 6. 和 C-REL(中继成员资格校验)的关系

C-REL 让中继记住每个群的主管理员公钥 `apk`,只接受它签的开群凭证 `ras` 来升 epoch。

- **建议第一步(ADM-1):换钥匙仍只能由主管理员做。** 中继完全不用改,C-REL 原样实现。副管理员能发公告、批准设备,不能换钥匙。
- 第二步(ADM-2,可选):副管理员也能换钥匙。`ras` 旁边附上管理员名单,中继验「主管理员签的名单里有这把钥匙」
  并记住见过的最大名单版本(否则被撤销的副管理员可以拿旧名单继续升 epoch)。中继会因此多记一个数字。
  建议等真有群需要时再做。

## 7. 协议改动清单(都是可选字段,旧客户端忽略)

| 位置 | 新增 | 旧客户端 |
|---|---|---|
| 消息信封 `kind` | `admin-set`、`roster`、`join-request`、`admin-request` | 不认识的 kind 已被忽略(需在实现时用测试确认) |
| `AnnouncementEnvelope` | `adminKeyId` | 用主管理员公钥验副管理员的公告 → 验不过 → **看不到副管理员发的公告**(过渡期代价,要写进发布说明) |
| SIC2 邀请串 | `ivs`(一人一码秘密,约 43 字符) | 忽略 |
| 本机加密存储 | 管理员名单、设备名单、已发出的一人一码邀请 | — |
| `JoinedGroup` | 名单要像 `adminPublicKeyRawB64Url` 一样持久化(手册 4.4 的教训) | — |
